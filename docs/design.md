# こえわけ 設計メモ

技術選定の理由と、Phase 2 の計画。

> 「要件 §N」は、このリポジトリには入っていない要件メモの節番号を指す。

## 決めたこと

### 1. 音声認識はローカル（faster-whisper）

**クラウドAPIではなくローカルにした。**

| | ローカル (採用) | クラウドAPI |
|---|---|---|
| ランニングコスト | 0円 | 週4〜5本のライブ配信だと積み上がる |
| 配信素材の扱い | PCの外に出ない | アップロードが必要 |
| 初回の待ち | モデル1.5GBのDL | すぐ使える |
| 速度 | PC性能次第 | 安定して速い |
| アカウント管理 | 不要 | APIキーの発行・更新を利用者が管理することになる |

決め手は**利用者が自分だけで回せること**（要件 §3）。APIキーの管理や
残高切れが「開発者に聞かないと動かない」原因になるのを避けた。

PCスペックが未確認（要件 §7）なので、**遅かったら品質を落として逃げられる**ようにしてある。

- `--quality fast` … `small`。かなり粗いが速い
- `--quality balanced` … `large-v3-turbo`（**既定**）
- `--quality accurate` … `large-v3`

NVIDIA GPU があれば自動で CUDA + float16 に乗る。無ければ CPU + int8。
Apple Silicon は CTranslate2 が Metal 非対応なので CPU 実行になる。

> 参考実測（M系 Mac / CPU int8 / balanced）: 35秒の音声で約1分。
> つまり **実時間の1.5〜2倍程度**。1時間の配信なら1.5〜2時間が目安。
> ここが実用に耐えないと分かったら `fast` に落とすか、`--device cuda` の
> 使える Windows 機で回す。

**差し替えできるようにしてある**: エンジンは `transcribe.py` の
`transcribe() -> list[Segment]` の中だけに閉じている。将来クラウドAPIに
変える場合も、この関数を差し替えれば他は触らずに済む。

### 2. UI は「ドラッグ＆ドロップ」＋ CLI

GUI アプリは作っていない。利用者の操作は
**動画をアイコンにドロップする**だけで足りるため。

- Windows … `scripts\koewake.bat` にドロップ（複数可）
- macOS … `scripts/koewake.command` を開いてウィンドウにドラッグ
  （macOS の Finder はシェルスクリプトへのドロップを受け付けないので、
  Terminal にパスをドラッグする形にした）

開発者側は `uv run koewake ...` で全オプションが使える。

### 3. 配布は「ZIP + セットアップスクリプト」

exe 化（PyInstaller）は**採らなかった**。CTranslate2 + CUDA を含む
one-file 化はビルドが壊れやすく、Windows 実機で検証できないうちは
「動かないexe」を渡す危険がある。

代わりに、`setup-windows.bat` / `setup-macos.command` が
uv（単体バイナリ1つ）を自動で入れ、Python ごと環境を用意する。
利用者の操作は**ダブルクリック1回**で、実質 exe と同じ手数になる。

将来、頻繁に配り直す必要が出てきたら exe 化を再検討する。

### 4. 字幕の整形ルール

Whisper のセグメントはそのままだと1枚に100文字以上入ることがあり、字幕として読めない。
`subtitle.py` で3段階に整形する。

1. **分割** — 文を単位にする。短い文は1枚にまとめ、長い文は**必要な枚数に等分**する
   - 上限まで詰めてから切ると「〜やっていきたい / と思います」のように
     末尾のひと言だけが次の字幕に取り残される。先に枚数を決めて等分することでこれを防ぐ
   - 最小枚数ぴったりだと切れる位置が残らないので、1〜2枚増やした場合も試して良い方を採る
2. **折り返し** — 横 20字×2行 / 縦 13字×2行（動画の縦横から自動判定）
3. **尺の調整** — 最短1.0秒・最長6.0秒・重なりを除去

分割と折り返しは**同じ「切って良い位置」の判定**を共有している。日本語には単語区切りが
無いので、次の3つを手がかりにしている。

| 手がかり | 例 | 判定 |
|---|---|---|
| 句読点 | `〜ですので、` | 最優先で切る |
| 文字種の変わり目 | ひらがな→漢字（`された\|新しい`） | 助詞のあとなので切って良い |
| | 漢字→ひらがな（`新\|しい`） | 送り仮名を割るので避ける |
| | カタカナの途中（`モンス\|ター`） | 語の途中なので避ける |
| 行頭の助詞 | `モンスター \| に挑戦して〜` | 助詞始まりは読みにくいので避ける |

> 「や」「も」「か」「ね」「よ」は助詞にもなるが語頭にも普通に立つ（やっていく・もう・かなり）ので、
> 行頭を避ける助詞には**入れていない**。

これらは 25,000 ケースのランダム入力で「1行の文字数」「1枚の行数」「時間の重なり」が
破られないことを確認してある（`tests/test_subtitle.py`）。

句読点は既定で落とす（日本語字幕の慣習）。`--keep-punctuation` で残せる。

### 5. 文字コードは UTF-8 (BOM付き)

Filmora(Windows) で日本語が化けにくい。`--encoding` で `utf-8` / `shift-jis` にも切り替えられる。
改行は SRT の慣習どおり CRLF。

### 6. 進捗表示

「本当に動いているのか分からない」が実際に一番つらいので、次の方針にしている。

- **描画は別スレッド**。処理が進んでいなくてもアニメーションは回り続ける
  （文字起こしは無音区間をまたぐと数十秒スコアが動かないことがある）
- **分からないときは％を出さない**。最初のひとまとまりが返るまでは「音声を解析しています」と
  経過時間だけを出す。0% のバーを置くと止まって見える
- **モデルのダウンロードも％で出す**。初回の 1.5GB が一番長い待ちなのに、
  faster-whisper は進捗を潰している（`tqdm_class=disabled_tqdm`）ので、
  `snapshot_download` を自前で呼んでバイト数を拾っている
- **端末でないときはアニメーションしない**。パイプやログに `\r` を撒かず、15秒ごとに1行出す
- 全角を2文字ぶんとして数え、端末幅で折り返さないようにしている。
  補足テキストを出す幅が足りないときは、断片を出さずに省く

モデルは**1回だけ読み込んで使い回す**（複数ファイルをドロップしても読み直さない）。

> ⚠️ 終了時のクラッシュについて
> CTranslate2 は後片付けでまれにクラッシュする（macOS の `recursive_mutex lock failed`）。
> 一度これを `os._exit()` で回避したが、multiprocessing の後始末を飛ばすため
> 「leaked semaphore」の警告が**毎回**出るようになり、かえって不安にさせるのでやめた。
> 今は普通に終了し、その前に `gc.collect()` でモデルを解放しきっている。

### 7. ハルシネーション対策

無音・BGMのみの区間で Whisper は「ご視聴ありがとうございました」等を高確率で吐く。
ゲーム実況はBGMと無音が多いので、そのままだと字幕に混入する。対策：

- Silero VAD で無音区間を除外
- `condition_on_previous_text=False`（一度ループし始めると延々続くのを防ぐ）
- 既知の定型句・同一文字の連呼をパターンで除去
- 同じセリフが3回を超えて連続したら切り捨て

## Phase 2（話者分離）

**実装済み。** `--speakers auto` または `--speakers 2` で、話者ごとに別々のSRTを出す。

### 1. pyannote.audio ではなく sherpa-onnx

| | sherpa-onnx（採用） | pyannote.audio |
|---|---|---|
| 依存 | ONNX Runtime のみ | PyTorch（数GB） |
| 事前準備 | モデルDL（35MB）のみ | HuggingFace のトークン発行と利用規約の同意が必要 |
| 配布 | 今の構成のまま | 利用者に規約同意の作業が発生する |

「利用者が自分だけで回せること」を守るなら、HFトークンが要る時点で pyannote は不利。

使うモデルは2つ。
- **話者の切れ目を見つける**: pyannote segmentation 3.0 を ONNX にしたもの（7MB）
- **声の特徴を数値にする**: 3D-Speaker CAM++（28MB）

後者に日本語専用のものは無いが、話者埋め込みは言語の影響を受けにくいので、
中国語・英語で学習したものをそのまま使っている。

> ⚠️ sherpa-onnx の依存の書き漏れ
> sherpa-onnx の wheel は 2MB しかなく、ネイティブライブラリの実体は
> `sherpa-onnx-core` にある。ところが wheel のメタデータにその依存が
> 書かれていないため、uv は core を入れてくれず、import が
> `libonnxruntime` 不足で落ちる。直るまでは pyproject.toml で
> **core を明示的に、同じバージョンで指定**している。

### 2. 話者の割り当ては単語単位で、そのあと均す

文字起こしの区間と話者の区間は境目が一致しない。そこで単語のタイムスタンプを使い、
話者が変わる位置で区間を分割している。

ただし、そのままだと**発話の最初の一語だけが前の話者に取られる**。

- 話者の区間には隙間がある（無音とみなされた部分）。そこに落ちた語は、
  時間的に近い方＝**前の話者**に寄ってしまう
- 境目をまたぐ語は、重なりの大きい方＝やはり前の話者になりやすい

実際、「おお、なるほど」の「おお、」や、「やった」の**「や」だけ**が
前の人のSRTに入るという壊れ方をした。単語の途中で別ファイルに分かれてしまう。

対策として、**0.6秒より短いひとかたまりは話者の切り替わりとみなさず**、
隣の長い方に吸収させている（`smooth_short_runs`）。
短い相づちを取りこぼす代わりに、語が割れることは無くなる。

### 3. 表示時間の調整は話者ごとに独立してかける

重なりの除去（`normalize_timing`）を全体にかけてはいけない。
別々のSRTとして**別トラックに載せる**ので、話者どうしの発言が時間的に
重なるのはむしろ自然であり、そこをずらすと音とズレる。

### 4. 話者番号は「喋り始めた順」

クラスタリングが返す番号は実行ごとに変わりうるので、そのままファイル名にすると
`話者1` が誰なのか安定しない。最初に喋った人を `話者1` にしている。
`--speaker-names` もこの順で対応する。

### 5. ドラッグ＆ドロップでは1回だけ人数を聞く

`koewake.command` / `koewake.bat` は、ドロップ後に1回だけ聞く。

```
話者ごとに別々のSRTに分けますか？
  そのまま Enter → 分けない（1本のSRT）
  人数を入力     → その人数で分ける（例: 2）
  a              → 人数もおまかせで判定
```

一度は「常に `--speakers auto`」にしたが、**3人以上で人数を外す**ことが分かったため、
聞く形に戻した（下の計測を参照）。人数を外すと1人が2ファイルに割れて実害が出る。
ソロ配信なら Enter だけなので、手数はほぼ変わらない。

### 5-1. 計測：人数が増えると当たらなくなる

合成音声（macOS の `say`）で会話を作り、どの時刻が誰の発言かを正解として測った。

| 人数 | 人数を指定 | `auto` |
|---|---|---|
| 1人 | ✓ 100% | ✓ 100% |
| 2人 | ✓ 100% | ✓ 100% |
| 3人 | ✓3人 72.1% | ✗2人と誤判定 71.4% |
| 4人(A) | ✓4人 84.3% | ✗5人と誤判定 84.3% |
| 4人(B) | ✗3人 64.0% | ✗3人と誤判定 64.0% |

**人数指定は auto と同等以上**で、3人・4人では人数そのものを当てられる。
`auto` はここを外すので、ドラッグ＆ドロップでも人数を聞くことにした。

### 5-2. 精度を上げようとして、やめたこと

`auto` が人数を外す問題を、次の2通りで直そうとしたが**どちらも採らなかった**。

**(a) クラスタリングの閾値を変える** — 0.4〜0.9 を掃引した。
1人・2人はどの値でも100%。3人が当たるのは 0.75 のときだけで、
そこでも4人は外す。**全体を良くする値が存在しない**。

**(b) 埋め込みモデルを変える** — 4種類を比較した。
`campplus zh-cn` は auto で 1/2/3/4人すべての人数を当て、現行より良く見えた。
ところが**別の声で作った2本目の4人サンプルでは逆転**し（現行 64.0% / zh-cn 58.6%）、
どちらも3人に潰れた。1サンプルで見えた差が別サンプルで消える以上、
乗り換えれば過剰適合になる。`wespeaker CAM++ LM` は2人を6人に割るなど明確に悪かった。

現行の `campplus zh_en` を据え置き、**人数を指定できる導線を用意する**ことで対処した。

> ⚠️ この計測は macOS の合成音声によるもので、同じ音声合成エンジンの声どうしは
> 実際の人間より似ている可能性が高い。**実配信での数字は別に取り直す必要がある**。

### 5-3. 音声が複数トラックある動画

マイクを人ごとに分けて録っていれば、推測に頼らず確実に分けられる。
そこで**音声トラックが複数あれば全部読み、トラックごとに字幕を作る**。

`ffmpeg -i` の出力から音声ストリームの本数と名前を拾い、
`-map 0:a:N` でトラックを選んで取り出している。
名前（mp4 は `name`、mkv は `title`）が入っていればファイル名に使う。

**トラックが分かれていても、その中で話者判別はする。**
1本のマイクを2人で共有していることがあるため（トラックA＝Aさん、
トラックB＝BさんとCさん、など）。

接尾辞は、区別に要るぶんだけ付ける。

| | 出力 |
|---|---|
| 1トラック・1人 | `動画.srt` |
| 1トラック・複数人 | `動画_話者1.srt` |
| 複数トラック・そのトラックは1人 | `動画_トラック1.srt` |
| 複数トラック・そのトラックに複数人 | `動画_トラック1_話者1.srt` |

`--speakers` はトラックごとに指定できる（`1,2`）。
`--speaker-names` は **トラック順 → 話者順** に割り当て、
名前が付いた出力にはトラック名を足さない（`動画_Cさん.srt`）。

> 話者番号はトラックごとに1から振り直す。別トラックの「話者1」は別人なので、
> 通し番号にすると誤解のもとになる。

**検証**: トラック1＝1人、トラック2＝2人の動画を作って確認した。
9発話すべてが正しいファイルに入り、名前指定でも意図どおりに並んだ。

### 6. モデルの置き場所

`~/Library/Caches/koewake`（macOS）/ `%LOCALAPPDATA%\koewake`（Windows）/
`~/.cache/koewake`（Linux）。`KOEWAKE_CACHE_DIR` で変更できる。

### 検証

macOS の `say` で2人の日本語音声（男女）を作り、どの時刻が誰の発言かを
正解データとして持たせて確認した。47秒・10発話・話者2人で、
**10発話すべてが正しい方のSRTに入る**ところまで確認している。

実際のコラボ配信（BGM・笑い声・同時発話あり）ではここまでの精度は出ないはずなので、
1本試してから判断する。

## 未確定のまま残っていること（要件 §7）

実装では**保守的な既定値**を置いて、後から変えられるようにしてある。

| 項目 | 今の扱い |
|---|---|
| 利用者のPCスペック | `--quality` で3段階に逃げられる。実測してから既定を決め直す |
| 精度の要件 | `--vocab` で固有名詞を渡せる。まず1本試して判断する |
| 話者名の付け方 | `話者1` `話者2` で出し、`--speaker-names` で改名できる形にした |
| Filmora で他に困っていること | 未着手。字幕以外は Filmora で足りている前提 |
