# こえわけ 設計メモ

技術選定の理由と、Phase 2 の計画。

> 「要件 §N」は、このリポジトリには入っていない要件メモの節番号を指す。

## 決めたこと

### 1. 音声認識はローカル（faster-whisper）

**クラウドAPIではなくローカルにした。**

| | ローカル (採用) | クラウドAPI |
|---|---|---|
| ランニングコスト | 0円 | 週4〜5本のライブ配信だと積み上がる |
| 配信素材の扱い | PCの外に出ない | アップロードが必要 |
| 初回の待ち | モデル1.5GBのDL | すぐ使える |
| 速度 | PC性能次第 | 安定して速い |
| アカウント管理 | 不要 | APIキーの発行・更新を利用者が管理することになる |

決め手は**利用者が自分だけで回せること**（要件 §3）。APIキーの管理や
残高切れが「開発者に聞かないと動かない」原因になるのを避けた。

PCスペックが未確認（要件 §7）なので、**遅かったら品質を落として逃げられる**ようにしてある。

- `--quality fast` … `small`。かなり粗いが速い
- `--quality balanced` … `large-v3-turbo`（**既定**）
- `--quality accurate` … `large-v3`

NVIDIA GPU があれば自動で CUDA + float16 に乗る。無ければ CPU + int8。
Apple Silicon は CTranslate2 が Metal 非対応なので CPU 実行になる。

> 参考実測（M系 Mac / CPU int8 / balanced）: 35秒の音声で約1分。
> つまり **実時間の1.5〜2倍程度**。1時間の配信なら1.5〜2時間が目安。
> ここが実用に耐えないと分かったら `fast` に落とすか、`--device cuda` の
> 使える Windows 機で回す。

**差し替えできるようにしてある**: エンジンは `transcribe.py` の
`transcribe() -> list[Segment]` の中だけに閉じている。将来クラウドAPIに
変える場合も、この関数を差し替えれば他は触らずに済む。

### 2. UI は「ドラッグ＆ドロップ」＋ CLI

GUI アプリは作っていない。利用者の操作は
**動画をアイコンにドロップする**だけで足りるため。

- Windows … `scripts\koewake.bat` にドロップ（複数可）
- macOS … `scripts/koewake.command` を開いてウィンドウにドラッグ
  （macOS の Finder はシェルスクリプトへのドロップを受け付けないので、
  Terminal にパスをドラッグする形にした）

開発者側は `uv run koewake ...` で全オプションが使える。

### 3. 配布は「ZIP + セットアップスクリプト」

exe 化（PyInstaller）は**採らなかった**。CTranslate2 + CUDA を含む
one-file 化はビルドが壊れやすく、Windows 実機で検証できないうちは
「動かないexe」を渡す危険がある。

代わりに、`setup-windows.bat` / `setup-macos.command` が
uv（単体バイナリ1つ）を自動で入れ、Python ごと環境を用意する。
利用者の操作は**ダブルクリック1回**で、実質 exe と同じ手数になる。

将来、頻繁に配り直す必要が出てきたら exe 化を再検討する。

### 4. 字幕の整形ルール

Whisper のセグメントはそのままだと1枚に100文字以上入ることがあり、字幕として読めない。
`subtitle.py` で3段階に整形する。

1. **分割** — 文を単位にする。短い文は1枚にまとめ、長い文は**必要な枚数に等分**する
   - 上限まで詰めてから切ると「〜やっていきたい / と思います」のように
     末尾のひと言だけが次の字幕に取り残される。先に枚数を決めて等分することでこれを防ぐ
   - 最小枚数ぴったりだと切れる位置が残らないので、1〜2枚増やした場合も試して良い方を採る
2. **折り返し** — 横 20字×2行 / 縦 13字×2行（動画の縦横から自動判定）
3. **尺の調整** — 最短1.0秒・最長6.0秒・重なりを除去

分割と折り返しは**同じ「切って良い位置」の判定**を共有している。日本語には単語区切りが
無いので、次の3つを手がかりにしている。

| 手がかり | 例 | 判定 |
|---|---|---|
| 句読点 | `〜ですので、` | 最優先で切る |
| 文字種の変わり目 | ひらがな→漢字（`された\|新しい`） | 助詞のあとなので切って良い |
| | 漢字→ひらがな（`新\|しい`） | 送り仮名を割るので避ける |
| | カタカナの途中（`モンス\|ター`） | 語の途中なので避ける |
| 行頭の助詞 | `モンスター \| に挑戦して〜` | 助詞始まりは読みにくいので避ける |

> 「や」「も」「か」「ね」「よ」は助詞にもなるが語頭にも普通に立つ（やっていく・もう・かなり）ので、
> 行頭を避ける助詞には**入れていない**。

これらは 25,000 ケースのランダム入力で「1行の文字数」「1枚の行数」「時間の重なり」が
破られないことを確認してある（`tests/test_subtitle.py`）。

句読点は既定で落とす（日本語字幕の慣習）。`--keep-punctuation` で残せる。

### 5. 文字コードは UTF-8 (BOM付き)

Filmora(Windows) で日本語が化けにくい。`--encoding` で `utf-8` / `shift-jis` にも切り替えられる。
改行は SRT の慣習どおり CRLF。

### 6. 進捗表示

「本当に動いているのか分からない」が実際に一番つらいので、次の方針にしている。

- **描画は別スレッド**。処理が進んでいなくてもアニメーションは回り続ける
  （文字起こしは無音区間をまたぐと数十秒スコアが動かないことがある）
- **分からないときは％を出さない**。最初のひとまとまりが返るまでは「音声を解析しています」と
  経過時間だけを出す。0% のバーを置くと止まって見える
- **モデルのダウンロードも％で出す**。初回の 1.5GB が一番長い待ちなのに、
  faster-whisper は進捗を潰している（`tqdm_class=disabled_tqdm`）ので、
  `snapshot_download` を自前で呼んでバイト数を拾っている
- **端末でないときはアニメーションしない**。パイプやログに `\r` を撒かず、15秒ごとに1行出す
- 全角を2文字ぶんとして数え、端末幅で折り返さないようにしている。
  補足テキストを出す幅が足りないときは、断片を出さずに省く

モデルは**1回だけ読み込んで使い回す**（複数ファイルをドロップしても読み直さない）。

> ⚠️ 終了時のクラッシュについて
> CTranslate2 は後片付けでまれにクラッシュする（macOS の `recursive_mutex lock failed`）。
> 一度これを `os._exit()` で回避したが、multiprocessing の後始末を飛ばすため
> 「leaked semaphore」の警告が**毎回**出るようになり、かえって不安にさせるのでやめた。
> 今は普通に終了し、その前に `gc.collect()` でモデルを解放しきっている。

### 7. ハルシネーション対策

無音・BGMのみの区間で Whisper は「ご視聴ありがとうございました」等を高確率で吐く。
ゲーム実況はBGMと無音が多いので、そのままだと字幕に混入する。対策：

- Silero VAD で無音区間を除外
- `condition_on_previous_text=False`（一度ループし始めると延々続くのを防ぐ）
- 既知の定型句・同一文字の連呼をパターンで除去
- 同じセリフが3回を超えて連続したら切り捨て

## Phase 2（話者分離）の計画

**まだ実装していない。** 要件メモ §5 の指示どおり Phase 1 の実運用を確認してから着手する。

### 方針

**pyannote.audio ではなく sherpa-onnx を第一候補にする。**

| | sherpa-onnx | pyannote.audio |
|---|---|---|
| 依存 | ONNX Runtime のみ | PyTorch（数GB） |
| 事前準備 | モデルDLのみ | HuggingFace のトークン発行と利用規約の同意が必要 |
| 配布 | 今の構成のまま | 利用者に規約同意の作業が発生する |

「利用者が自分だけで回せること」を守るなら、HFトークンが要る時点で pyannote は不利。
精度が足りなければ再検討する。

### 差し込み口はもう空けてある

- `Segment.speaker: str | None` — 話者を入れる席（Phase 1 では常に `None`）
- `Cue.speaker` — キューまで話者情報が流れる
- `--save-transcript` で出る JSON — 文字起こしをやり直さずに分離を試せる

### 実装の流れ（予定）

1. `diarize.py` を足す … 音声 → `[(start, end, speaker_id)]`
2. 各 `Segment` を、時間の重なりが最大の話者に割り当てる
3. `build_cues` の結果を話者ごとに分けて、`動画名_話者1.srt` のように別ファイルで書く
4. 話者名は `--speaker-names ホスト,ゲスト1` で後から差し替えられるようにする
   （要件 §7 の未確定事項。まず `話者1` `話者2` で出して、名前は後付けが無難）

## 未確定のまま残っていること（要件 §7）

実装では**保守的な既定値**を置いて、後から変えられるようにしてある。

| 項目 | 今の扱い |
|---|---|
| 利用者のPCスペック | `--quality` で3段階に逃げられる。実測してから既定を決め直す |
| 精度の要件 | `--vocab` で固有名詞を渡せる。まず1本試して判断する |
| 話者名の付け方 | Phase 2 で `話者1` `話者2` 固定 + 後から改名できる形を想定 |
| Filmora で他に困っていること | 未着手。字幕以外は Filmora で足りている前提 |
